本文件是 SKILL.md 各阶段的细化操作清单，供执行时对照。所有与用户的沟通使用简体中文。

## 注释符约定（所有阶段通用，写配置前必读）

不同厂商的配置注释符不同，**混用会导致华为/华三设备粘贴报错**，必须按厂商分派：

| 厂商 | 标准注释/分段符 | 错误做法 | 后果 |
|------|----------------|----------|------|
| 思科 Cisco（IOS/IOS-XE） | `!` | 用 `#` | 思科不把 `#` 当注释，会尝试解析报错 |
| 华为 Huawei（VRP） | `#` | 用 `!` | VRP 报 `Error: Unrecognized command`，中断部署 |
| 华三 H3C（Comware） | `#` | 用 `!` | Comware 报 `Error: Unrecognized command`，中断部署 |

操作规则：
- 阶段 7 写每台配置前，**先确认该设备品牌**，整文件统一使用其标准注释符；不要跨厂商混用。
- 华为/华三里 `#` 同时是官方配置文件的段落分隔符，作为注释/分段使用完全合规；纯 `#` 空行也是合法分隔。
- 写完后若担心串味，用归一化脚本一键修正：

  ```
  python scripts/normalize_comments.py --vendor huawei --in DSW1_三层交换机_v1.txt --in-place
  python scripts/normalize_comments.py --vendor h3c    --in ASW1_二层交换机_v1.txt --in-place
  python scripts/normalize_comments.py --vendor cisco  --in R1_出口设备_v1.txt      --in-place
  ```

  脚本把所有以 `!` 或 `#` 开头的行统一改成目标厂商注释符；非注释行不动。
- **引用参考文件命令时，注释符以目标厂商为准**：思科参考里的 `!` 可直接用；华为/华三参考里的 `#` 可直接用；**不要照搬示例中的注释字符到错误厂商**（例如把华为参考里的 `#` 当思科 `!` 用，或反之）。

> **总原则（贯穿阶段 1–5）**：阶段 1–5 是"咨询与确认"，不是产出。每个阶段结束前都必须拿到用户明确确认。即使用户说"你自行决定/随便/你看着办"，也**必须列出含推荐项的选项清单**让用户确认或改选，绝不允许静默默认关键项（例如不能说"文档没提 NAT 我就按纯路由做了"——必须先把"是否做 NAT"抛给用户选）。阶段 6/7 才真正写文档和配置。

## 阶段 3 · 关键决策提问模板（必须暂停 · 列选项等确认）

用 `AskUserQuestion` 抛出，选项含"其他"。若用户已在阶段 1/2 明确给出某项，可跳过该项。
**即使某项是用户授权你"自行决定"的，也必须把推荐项放在选项里让用户确认/改选。**

### 决策清单（建议逐批抛出，每批 1–4 问）

**问题 1 — 路由协议**
- 选项：OSPF（推荐，园区网通用）/ IS-IS / 静态路由为主 / BGP（多出口或运营商互联）
- 追问（若选 OSPF）：进程号、区域划分（建议核心 area 0，接入非 0）、router-id 来源（Loopback）。

**问题 2 — 防火墙高可用**
- 选项：主备热备（HRP+VRRP，推荐）/ 负载分担（双主）/ 单机（无冗余）

**问题 3 — NAT 策略（⚠️ 必须显式问，禁止默认跳过）**
- 选项：出方向 PAT 出公网（内网共享公网 IP，推荐）/ 仅 DMZ 静态一对一映射 / 双向 NAT / **暂不需要 NAT（纯模拟网/内网互通）**
- 说明：若用户此前没提 NAT，绝不能自行假设"不做"——把"暂不需要 NAT"也作为一个明确选项抛给用户选。

**问题 4 — 链路聚合与虚拟化**
- 选项：需要 LACP 链路聚合 / 需要设备堆叠（iStack/IRF/vPC）/ 两者都要 / 都不需要

**问题 5 — DHCP 策略**
- 选项：核心/汇聚交换机做 DHCP 服务器 / 出口路由器做 DHCP 服务器 / 独立 DHCP 服务器 / 由上游下发（中继 relay）

**问题 6 — 管理与认证**
- 选项：启用 AAA+RADIUS（不可达回退本地，推荐）/ 仅本地账号 / 接入 TACACS+ ；并确认管理网段。

**问题 7 — 监控与故障检测**
- 选项：启用 SNMP+Syslog / 启用 BFD/NQA 链路检测 / 全部启用（推荐）/ 暂不配置

**问题 8 — 二层安全防护**
- 选项：端口安全+Sticky / DHCP Snooping+DAI / 802.1x(RADIUS) / MAC 黑名单 / 组合勾选 / 暂不需要

> 任何一项用户未回答（或只是笼统说"你定"而未对选项表态）前，不得进入阶段 4。可一次问 1–4 个，分轮完成；每轮结束时复述已确认项，再问下一批。

**结束条件**：上述决策清单全部获用户明确表态（含"采纳推荐项"），才进阶段 4。

## 阶段 4 · 完整草案生成与确认（必须暂停 · 列选项等确认）

AI 自动补全的非必要项及默认规则（**这些可以自定，但必须列在草案里供审查**）：
- **VLAN ID**：从 10 起按业务递增（管理 10、业务 20、语音 30、DMZ 40…）， trunk 放行所需列表。
- **互联接口**：按设备上联口顺序取（如 GE0/0/1、GE1/0/1），下联对应。
- **链路 IP**：互联网段用 /30，管理用 /24，业务按规模。
- **router-id / Loopback0**：取 `x.x.x.x`（如核心 1.1.1.1、2.2.2.2）。
- **LACP 组号**、**VRRP 组号**、**OSPF 进程号**默认从 1 起。

草案回显内容必须包含：
1. 拓扑草案（ASCII 框图，参考 `references/topology_examples.md`）；
2. 设备台账初稿（命名/型号/IP/互联）；
3. **关键决策落地点**（明确写出阶段 3 每项决策怎么落地，例如"NAT：R1 做出方向 PAT，匹配 10.0.0.0/8，转换到公网 200.1.1.x"）；
4. 协议与策略规划（VLAN、OSPF、VRRP、MSTP、LACP、ACL 编号与用途等）。

话术示例："以下非必要项由我代为规划，**阶段 3 的关键决策均已按你的确认落地**。请逐项审查；如需调整请指出具体项。确认'没问题'后我才进入可行性分析。"
**结束条件**：用户明确回复"没问题/确认"（或提出调整后你已修订并再次获确认），才进阶段 5。

## 阶段 5 · 可行性分析（必须暂停 · 列问题/方案等确认）

逐项打勾审查，并把"问题 → 影响 → 解决方案"报给用户，**每条方案都给选项让用户确认或改选**：

| 类别 | 检查点 | 常见问题 | 解决方案（须用户确认） |
|------|--------|----------|----------|
| IP | 冲突/掩码/互联余量 | 同网段重复、/24 当 /30 用 | 重划网段、改用 /30 |
| 路由 | 黑洞/环路/次优 | 缺默认路由、防火墙拦 OSPF | 下发 default-info、放行协议 |
| 二层 | 根桥/Trunk 一致性 | 根桥未指定导致震荡 | 手动 `root primary`、收敛 allow 列表 |
| 高可用 | 脑裂/抢占 | VRRP 优先级相同、BFD 时长不匹配 | 设优先级差、统一检测时长 |
| 安全 | ACL 方向/DMZ 暴露 | 方向反、通配符错 | 复核 in/out、最小放行 |
| 厂商能力 | 型号支持度 | C2960 不能跑 OSPF | 改由三层交换机承担路由 |
| 命令可得性 | CLI 语法/新机型 | 记忆无该型号命令、版本差异 | **上网查证官方文档（见 web_research.md）** |

> **跨厂商聚合/堆叠硬性规则（踩坑沉淀）**：**同厂商**（如两台华为 DSW）之间可做 LACP/Eth-Trunk、iStack/IRF/堆叠；**跨厂商**设备之间（如华为 DSW ↔ 华三 ASW、思科 ↔ 华为）**不要做 LACP/堆叠**（私有协议不互通），跨厂商上联一律用**静态 Trunk**（dot1q，`allow-pass`/`permit` 收敛放行列表）。此项在阶段 5 必须作为可行性检查点，违反则报告并改为静态 Trunk。

> **设计基线持久化（阶段 5 结束动作）**：可行性分析全部确认后，把锁定的设计（设备清单、VLAN/编址、互联、协议、关键决策、风险处理方案）写入项目目录下的 `设计基线.md`，作为阶段 6/7 与后续 v2/v3 增强的唯一依据；若会话中断，可据此恢复而不必重新确认。

报告末尾必须明确问用户："以上风险处理方案是否都按我建议的来？还是某项要改选？" 例如对根桥可抛："A 手动指定 DSW1 为 MST 总根(推荐) / B 保持自动选举"。
**结束条件**：用户对全部风险处理方案明确确认（或改选后再次确认）、你已无未决歧义，才进阶段 6。

## Web 命令查证流程（记忆缺失 / 新机型时必做）

详见 `references/web_research.md`。要点：
1. 在阶段 5 与阶段 7 前各做一次"命令可得性检查"：遍历所有设备型号，凡 `references/*.md` 未覆盖或你担心有版本差异的，标记"待查证"。
2. 用 `WebSearch` 检索厂商官方 Configuration Guide / 命令参考（Cisco / 华为 / 华三 入口见 web_research.md）。
3. 用 `WebFetch` 打开最相关官方页，提取准确命令片段与上下文。
4. 把查证结果用于写配置；若官方页不可达，退查社区/博客并在文件注释标注"未经官方二次确认"。
5. 反复用到的验证命令，补充进 `references/*.md`（SkillManage 累积）。
6. 向用户说明："已联网核对 X 型号命令"。注意：查证只解决命令准确性，不替代阶段 3/4/5 的决策确认。

## 阶段 7 之后 · 增强轮次（8 / 9，用户可选）

阶段 7（含 7.5 验收）完成后，用 `AskUserQuestion` 询问用户是否需要下列增强（可多选）：
- **8 安全加固基线**：对全网设备叠加 `references/hardening.md` 的加固项（禁用 Telnet/HTTP、仅 SSH v2、管理平面隔离、NTP、Syslog、控制平面保护等）。
- **9 参考库小补全应用**（已固化进技能参考文件，此处为"是否据此刷新交付物"）：拓扑范例 C（纯交换园区）、glossary 增补（MLAG/iStack/IRF、VXLAN、QoS、NTP、route-map/PBR）、MST 实例与 workflow 一致化。

若用户选择任一增强，进入**增强轮次**：
1. 以 `设计基线.md` 为依据，在原设计上叠加 8 / 9 内容；
2. 重新生成**版本化交付物**：文档命名 `项目设计文档_v2.docx`，每台配置命名 `<主机名>_<角色>_v2.txt`（v2、v3… 依增强轮次递增）；
3. 在文档中新增「安全加固说明 / 参考补全说明」章节，并说明与 v1 的差异点；
4. 配置变更部分同样跑 `normalize_comments.py` 归一化注释符；
5. 重新走一次 阶段 7.5 验收清单（仅验证受影响项）。

> 版本号规则：v1 为初版；每次"用户确认要增强"生成下一个版本号，旧版本文件保留不覆盖，便于回退比对。
